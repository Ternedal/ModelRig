# Memory 4.0 W04-B — stream-preserving normal-chat post-turn persistence

W04-B is the first reviewed integration slice that may connect a completed normal `/api/v1/chat` turn to the already-landed W04-A loopback write surface. It does **not** make memory writes unconditional and it does not move durable-memory authority into the backend or the model.

## Activation

The backend write hook is independently default-off:

- `KALIV_MEMORY4_CHAT_WRITE_ENABLED=1` enables W04-B observation/post-turn submission;
- `KALIV_MEMORY4_CHAT_ENABLED=1` remains the independent R05 read/context flag;
- `KALIV_MEMORY4_WRITE_ENABLED=1` remains the independent worker-side W04-A route flag.

With the W04-B flag off, the existing R05 handler is entered directly. With both chat flags off, `/api/v1/chat` remains the pre-Memory-4 direct Ollama proxy path: no request probe, response wrapper or memory-worker call is introduced.

`production_activation=false` in this slice: repository code gains the opt-in path, but no launcher/default/environment is changed to enable it.

## Streaming contract

W04-B does not modify `internal/proxy` and does not buffer the model response before returning it to the client. A narrow `http.ResponseWriter` observer lives in the HTTP API layer:

1. every status/header/body write is delegated to the original writer;
2. every `Flush()` is delegated immediately;
3. the same bytes are examined synchronously only to build a bounded candidate assistant transcript;
4. malformed, truncated, oversized or nonterminal output disables persistence but never changes the bytes already sent to the client.

The observer accepts bounded Ollama chat JSON/NDJSON only. Durable submission requires:

- an upstream 2xx response;
- valid assistant frames;
- assistant text within the W01 completed-turn bound (16,000 Unicode code points);
- exactly one valid terminal `done=true` frame;
- a non-empty canonical assistant transcript.

A client write failure, upstream non-2xx status, missing terminal frame or invalid stream therefore produces no W04-A call.

## Original-user binding

The backend probes the original bounded chat request before R05 may inject memory reference data. W04-B keeps only the original final text-user value, canonicalized with the same conservative length boundary used by W01.

If R05 retrieval is also enabled, the model may receive an injected `KALIV MEMORY DATA` reference block, but W04-B submits only the original current-user text to W04-A. Injected memory context can never become the `user_text` of the completed-turn write request.

`source_ref` is generated by the backend as a random `chat:<128-bit hex>` identifier. Client request IDs or model output cannot choose durable provenance.

## Worker boundary

Post-turn submission is allowed only to a loopback `Worker` target and only to:

`POST /experimental/memory4/commit-completed-turn`

The request contains exactly:

- `user_text`;
- `assistant_text`;
- server-created `source_ref`.

W04-B accepts only the exact value-free W03 receipt schema from W04-A. The response is bounded, required fields are checked, unknown fields are rejected, counts/IDs/action partitions are revalidated and mutation/replay invariants must match W03. Candidate values, evidence, model output or source provenance have no accepted response field.

## Failure semantics

The W04-A request runs synchronously after the terminal model frame; there is no goroutine, retry daemon, queue or scheduler authority. If W04-A is disabled, refuses the write, times out or returns an invalid receipt, W04-B discards the memory error. It does not append an error frame, replace the already-streamed response or change a successful chat status.

A non-loopback/missing worker disables W04-B persistence for that turn. If R05 read memory is enabled, its pre-existing fail-closed loopback semantics remain unchanged; W04-B does not weaken them.

## Authority preserved

W04-B does not decide what becomes durable memory. It only provides one completed turn to W04-A. The existing chain remains authoritative:

`normal chat -> W04-B bounded completed turn -> W04-A loopback route -> W03 turn binding -> W01 candidate authority -> W02 fresh transactional plan/write`

W04-B adds no direct create/correct/delete/supersede operation, no cloud write target, no Agent 3 activation, no tool approval authority and no protected-sidecar migration.

## Qualification focus

The W04-B Go qualification covers:

- both chat flags off: exact direct-proxy request behavior and no worker call;
- write-only mode: exact client stream bytes, forwarded flushes, original model request and one post-terminal W04-A call;
- R05 read + W04-B write composition: injected context reaches the model but not durable `user_text`;
- server-owned provenance;
- malformed, truncated and oversized response suppression without stream mutation;
- W04-A refusal after terminal chat is non-fatal;
- non-loopback worker suppresses persistence without breaking write-only chat;
- strict W03 receipt validation rejects unknown/value-like response fields.

W04-B remains an explicit opt-in integration boundary. Enabling it operationally still requires the backend flag and a separately enabled W04-A worker surface.
